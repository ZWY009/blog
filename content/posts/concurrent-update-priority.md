上个月我改了列表页的状态更新方式：把用户输入触发的更新全部提到最高优先级，理由是「输入必须立刻响应」。

改完体感确实更「跟手」了。但一周后看数据，**P75 首次可交互时间从 1.8s 涨到 2.1s**。

## 问题出在哪

高优先级更新会打断正在进行的渲染。当一屏里有十几个独立更新的组件时，每个输入事件都会插队，导致第一次完整渲染被切成很多碎片，用户看到的「能用」被推后。

```
改前：渲染 1 次，1.8s 后可交互，中间卡一下
改后：渲染被打断 6 次，2.1s 后可交互，但每次输入都立刻有反馈
```

**「输入立刻响应」这个目标本身没错，错的是我把它做成了全局规则。**

## 现在的做法

只有真正需要即时反馈的更新（输入框的值本身）走高优先级，派生出来的列表重排走默认优先级：

```ts
// 输入框：立刻响应
setQuery(next);

// 派生结果：让渲染自己调度，不要插队
startTransition(() => {
  setFilteredResults(compute(next));
});
```

## 教训

优先级不是「越高越好」，它是在「响应速度」和「渲染完整性」之间做分配。把它当开关用，就是拿一个维度去换另一个维度。

判断标准应该是：**这个更新如果晚一帧，用户会不会觉得卡？** 会，才提优先级。
